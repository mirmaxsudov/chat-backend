# Authentication and Current User API

Frontend integration contract for login and loading the authenticated user's profile.

## Base URL

Local development server:

```text
http://localhost:8080
```

All REST endpoints below use the `/api/v1` prefix. Configure the origin separately in the frontend, for example:

```env
VITE_API_BASE_URL=http://localhost:8080/api/v1
```

The backend's default allowed browser origin is `http://localhost:3000`. A different frontend origin must be included in the backend's `CORS_ALLOWED_ORIGINS` configuration.

## Quick authentication flow

1. Send the user's phone number and password to `POST /api/v1/auth/login`.
2. Store `data.accessToken` and `data.expiresAt` from the successful response.
3. Send `Authorization: Bearer <accessToken>` when calling protected endpoints.
4. Call `GET /api/v1/users/me` to load the current user.
5. If a protected request returns `401`, clear the local authentication state and send the user to login.

There is currently no refresh-token, registration, logout, forgot-password, or password-reset endpoint. Logout is therefore a frontend action: discard the access token and cached user data. Once an access token expires, the user must log in again.

## 1. Login

```http
POST /api/v1/auth/login
Content-Type: application/json
Accept: application/json
```

Authentication is not required for this endpoint.

### Request body

```json
{
  "phoneNumber": "+998901234567",
  "password": "StrongPassword123!"
}
```

| Field | Type | Required | Rules |
| --- | --- | --- | --- |
| `phoneNumber` | string | yes | Must not be blank; maximum 32 characters. Leading/trailing whitespace is removed before authentication. |
| `password` | string | yes | Must not be blank; maximum 128 characters. It is not trimmed. |

The phone number must match the stored value after the request value is trimmed. The API does not currently normalize country codes, spaces, or punctuation.

### Success response

Status: `200 OK`

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "tokenType": "Bearer",
    "expiresAt": "2026-09-01T12:34:56.789Z"
  }
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `data.accessToken` | string | Signed JWT used to authenticate subsequent requests. |
| `data.tokenType` | `"Bearer"` | Scheme to use in the `Authorization` header. |
| `data.expiresAt` | ISO 8601 UTC timestamp string | Exact instant at which the access token expires. Use this server-provided value rather than assuming a fixed lifetime. |

The JWT uses HS256 and contains the user UUID in `sub`, plus `iss`, `aud`, `iat`, `exp`, `jti`, and a `roles` claim. These claims may be useful for optimistic UI, but authorization must never rely on client-side token decoding. The backend remains authoritative.

### Invalid credentials

Status: `401 Unauthorized`

The same message is deliberately returned for an unknown phone number and an incorrect password.

```json
{
  "message": "Invalid phone number or password",
  "httpStatus": "UNAUTHORIZED",
  "localDateTime": "2026-09-01 17:34:56",
  "code": 401
}
```

### Request validation error

Status: `400 Bad Request`

Validation responses from this endpoint are a field-to-message object, not the standard API error object:

```json
{
  "phoneNumber": "Phone number is required",
  "password": "Password is required"
}
```

Possible validation messages:

- `Phone number is required`
- `Phone number is too long`
- `Password is required`
- `Password is too long`

Malformed JSON or an unsupported content type can also produce a `400`/`415` response generated by Spring; frontend code should not assume every non-2xx response has exactly one error shape.

### Example

```ts
type ApiResponse<T> = {
  success: boolean;
  message: string;
  data: T;
};

type LoginRequest = {
  phoneNumber: string;
  password: string;
};

type LoginData = {
  accessToken: string;
  tokenType: "Bearer";
  expiresAt: string;
};

async function login(input: LoginRequest): Promise<LoginData> {
  const response = await fetch(`${API_BASE_URL}/auth/login`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Accept: "application/json",
    },
    body: JSON.stringify(input),
  });

  const body = await response.json();
  if (!response.ok) throw body;

  return (body as ApiResponse<LoginData>).data;
}
```

## 2. Get the current user (GET ME)

```http
GET /api/v1/users/me
Authorization: Bearer <accessToken>
Accept: application/json
```

No request body or query parameters are accepted. This endpoint requires a valid, unexpired access token.

### Success response

Status: `200 OK`

```json
{
  "success": true,
  "message": "User profile retrieved",
  "data": {
    "id": "3f77a8ad-4484-4b72-86ea-f3f0788e33b8",
    "phoneNumber": "+998901234567",
    "username": "security-test-user",
    "firstname": "Security",
    "lastname": "Tester",
    "roles": ["USER"]
  }
}
```

| Field | Type | Nullable | Notes |
| --- | --- | --- | --- |
| `data.id` | UUID string | no | Stable user identifier. |
| `data.phoneNumber` | string | no | The user's login phone number. |
| `data.username` | string | yes | Unique public username when set. |
| `data.firstname` | string | yes | First name when set. |
| `data.lastname` | string | yes | Last name when set. |
| `data.roles` | array | no | Unordered set of roles. Current values are `USER` and `ADMIN`; do not depend on array order. |

### Missing, invalid, or expired token

Status: `401 Unauthorized`

```json
{
  "message": "Authentication is required",
  "httpStatus": "UNAUTHORIZED",
  "localDateTime": "2026-09-01 17:34:56",
  "code": 401
}
```

Treat all three cases the same on the frontend: clear the invalid session and require login. A `403 Forbidden` uses the same error structure but has message `Access is denied`, status `FORBIDDEN`, and code `403`.

### User no longer exists

Status: `404 Not Found`

This can occur when the JWT is valid but its user was deleted or cannot be found.

```json
{
  "message": "User not found",
  "httpStatus": "NOT_FOUND",
  "localDateTime": "2026-09-01 17:34:56",
  "code": 404
}
```

### Example

```ts
type Role = "USER" | "ADMIN";

type CurrentUser = {
  id: string;
  phoneNumber: string;
  username: string | null;
  firstname: string | null;
  lastname: string | null;
  roles: Role[];
};

async function getMe(accessToken: string): Promise<CurrentUser> {
  const response = await fetch(`${API_BASE_URL}/users/me`, {
    headers: {
      Authorization: `Bearer ${accessToken}`,
      Accept: "application/json",
    },
  });

  const body = await response.json();
  if (!response.ok) throw body;

  return (body as ApiResponse<CurrentUser>).data;
}
```

## Shared frontend types

```ts
export type ApiResponse<T> = {
  success: boolean;
  message: string;
  data: T;
};

export type ApiError = {
  message: string;
  httpStatus: string;
  localDateTime: string; // yyyy-MM-dd HH:mm:ss (server-local time)
  code: number;
};

export type ValidationErrors = Record<string, string>;
```

Because validation errors and standard API errors differ, narrow error bodies defensively:

```ts
export function isApiError(value: unknown): value is ApiError {
  return (
    typeof value === "object" &&
    value !== null &&
    "message" in value &&
    "code" in value
  );
}
```

## Frontend implementation notes

- Always build the auth header as `Authorization: Bearer ${accessToken}`. Do not send only the raw JWT.
- Compare token expiry with `new Date(expiresAt).getTime()`. `expiresAt` is an absolute UTC instant.
- Consider a small clock-skew buffer (for example, mark the session expired 30 seconds early).
- Never log the password or access token, and do not put the token in URLs or query strings.
- In a browser-only SPA, token storage is a security decision. Memory is safest against persistent token theft but does not survive reloads; web storage survives reloads but is accessible to injected scripts. This API currently returns the token in JSON and does not set an HttpOnly cookie.
- On application startup, if a non-expired token exists, call GET ME before considering authentication fully restored.
- Do not infer a user's profile or permissions solely from cached data. Refresh GET ME after login and when restoring a session.
- Role checks should use membership such as `roles.includes("ADMIN")`, never array position.
- There is no server-side logout or token revocation endpoint in the current API.

## Minimal acceptance checklist

- Login submits JSON with `phoneNumber` and `password`.
- Field validation errors are shown next to the matching inputs.
- Invalid credentials show the generic backend message.
- Successful login stores the access token and its expiry.
- Protected requests include the Bearer header.
- GET ME populates the authenticated user state.
- A `401` clears the session and redirects to login.
- Logout clears the token and all user-specific cached state.
